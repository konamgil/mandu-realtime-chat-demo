# mandu-chat-demo 고도화 기획 (Demo-First)

작성일: 2026-02-14

## 목표
- 데모에서 바로 체감 가능한 안정성/운영성 기능을 먼저 구현
- 구현 중 드러난 반복 보일러플레이트를 Mandu 프레임워크 개선 제안으로 연결

## 우선순위

### P1. 메시지 입력 정책(검증/에러 노출) 강화
- **문제**: 빈 메시지/과도한 길이 입력 시 UX 불명확, 서버 계약이 느슨함
- **사용자 시나리오**
  1. 사용자가 메시지 전송
  2. 서버가 입력 정책 위반을 명시적 코드와 함께 반환
  3. UI가 에러를 즉시 표시
- **성공 기준**
  - 빈 텍스트 400 + `EMPTY_TEXT`
  - 500자 초과 422 + `TEXT_TOO_LONG`
  - UI에서 실패 사유가 즉시 노출

### P1. 초기 스냅샷 제한(limit)으로 재연결/초기 로드 경량화
- **문제**: 메시지 누적 시 초기 로드/재접속에 불필요한 전체 스냅샷 비용 발생
- **사용자 시나리오**
  1. 사용자가 데모 접속
  2. UI가 limit 기반 초기 스냅샷 요청
  3. 이후 SSE로 증분 수신
- **성공 기준**
  - `GET /api/chat/messages?limit=N` 동작
  - UI에서 초기 로드 개수(20/50/100) 선택 가능
  - limit 동작이 테스트로 보장됨

## Demo-First → Framework 연결 원칙
- 데모에서 재현 가능한 불편/중복만 프레임워크 제안으로 승격
- 본 배치에서 확인된 연결점
  1. **쿼리 파라미터 파싱/검증 반복** (`sinceId`, `limit` 수동 처리)
  2. **SSE/JSON 에러 응답 보일러플레이트 반복** (route별 수기 구현)
